# ADR-001. Оркестрация саги заказа подарка в Order Service

**Статус:** Принято
**Ответственный:** Алиса

## Контекст

Заказ подарка затрагивает Payment Service (холд и списание), Group Service (адрес подопечного) и внешний маркетплейс. Общей транзакции между ними нет: каждый сервис работает со своей базой, а маркетплейс вообще внешняя система. Любой шаг может не удаться, и тогда уже выполненные шаги нужно отменить (снять холд, отменить заказ). Значит, нужна сага. Вопрос в том, кто ей управляет.

## Рассмотренные варианты

**1. Хореография.** Сервисы реагируют на события друг друга: Payment публикует `payment.held`, Order на него заказывает товар и публикует `order.placed`, Payment на это списывает деньги и так далее.
- Плюсы: нет центрального координатора, сервисы слабо связаны.
- Минусы: логику процесса не видно ни в одном месте, она размазана по сервисам. Сложно понять, на каком шаге застрял конкретный заказ. Компенсации тоже приходится разносить по сервисам. Маркетплейс — внешняя система и событий в наш брокер не публикует, поэтому кто-то все равно должен его вызывать.

**2. Оркестрация в Order Service.** Order Service хранит состояние саги и по очереди вызывает участников, а при сбое сам запускает компенсации.
- Плюсы: весь процесс описан в одном месте, статус любого заказа виден в одной таблице, компенсации легко проследить и протестировать. Подходит для вызова внешнего маркетплейса.
- Минусы: Order Service знает об API других сервисов и становится важной точкой: если он недоступен, новые заказы не обрабатываются.

**3. Отдельный сервис-оркестратор** (или готовый движок вроде Temporal или Camunda).
- Плюсы: процессы отделены от бизнес-логики заказа.
- Минусы: еще один сервис или тяжелая инфраструктура ради одного процесса. Для команды из трех человек это избыточно.

## Решение

Выбираем вариант 2: оркестрация в Order Service.

- Состояние саги (`sagaStep`) хранится в `order_db` и сохраняется перед каждым шагом.
- Шаги и компенсации: `HOLD_PAYMENT` ↔ `RELEASE_PAYMENT`, `PLACE_MARKETPLACE_ORDER` ↔ `CANCEL_MARKETPLACE_ORDER`, `CAPTURE_PAYMENT` ↔ `REFUND_PAYMENT`. Шаг `GET_RECIPIENT_ADDRESS` только читает данные и компенсации не требует.
- Сага выполняется фоновым обработчиком, а не внутри HTTP-запроса: клиент сразу получает `202 Accepted`.
- Вызовы участников саги синхронные (REST) с ключами идемпотентности (см. [ADR-004](ADR-004-idempotency.md)).

## Последствия

- Весь главный процесс можно объяснить по одной sequence-диаграмме, а «где застрял заказ» видно по одной записи в базе.
- После падения Order Service сага продолжается с сохраненного шага (сценарий сбоя 2).
- Order Service зависит от API Payment и Group Service: изменения этих API нужно согласовывать.
- Если Order Service недоступен, новые заказы не принимаются, но остальная система (группы, жеребьевка, уведомления) работает.
- Нужен механизм таймаута: сага, которая стоит дольше 30 минут, завершается компенсацией (`TIMEOUT`).
