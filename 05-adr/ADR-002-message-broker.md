# ADR-002. RabbitMQ в качестве брокера сообщений

**Статус:** Принято
**Ответственный:** Анзор

## Контекст

Часть взаимодействий в системе асинхронная: Group Service сообщает о закрытии регистрации и выходе участников, Draw Service — о результатах жеребьевки, Order Service — о статусах заказов. Потребители (Draw, Order, Notification) должны получать события, даже если в момент публикации они были недоступны. Нужно выбрать, через что передавать события.

Особенности нашей нагрузки: событий немного (десятки на группу), порядок важен только внутри одной группы, хранить историю событий долго не нужно. Каждое событие нужно нескольким потребителям, и у каждого своя обработка.

## Рассмотренные варианты

**1. Без брокера: сервисы вызывают друг друга по REST.**
- Плюсы: нет дополнительной инфраструктуры.
- Минусы: источник должен знать всех потребителей и повторять вызовы, если кто-то недоступен. Падение Notification Service ломало бы выход участника из группы. Это сильная связанность.

**2. Apache Kafka.**
- Плюсы: высокая пропускная способность, события хранятся долго и их можно перечитать.
- Минусы: сложнее в настройке и эксплуатации, нет встроенных отложенных повторов и очередей «мертвых писем». Возможности потоковой обработки нам не нужны при нашем объеме событий.

**3. RabbitMQ.**
- Плюсы: проще в развертывании, есть маршрутизация по routing key (exchange типа topic), подтверждения обработки (ack), очереди «мертвых писем» из коробки. Хорошо подходит для схемы «одно событие — несколько потребителей со своими очередями».
- Минусы: сообщения удаляются после обработки, поэтому перечитать историю нельзя. Ниже пропускная способность, чем у Kafka, но для нас это не важно.

## Решение

Выбираем RabbitMQ.

- У каждого сервиса-источника свой exchange типа `topic`: `group.events`, `draw.events`, `order.events`.
- Routing key равен типу события (`group.participant-left`).
- У каждого потребителя своя durable-очередь `<сервис-потребитель>.<exchange>` с привязками только к нужным событиям.
- Сообщения persistent, подтверждение обработки ручное (ack после коммита в базу).
- После нескольких неудачных попыток сообщение попадает в `<очередь>.dlq` для разбора.

## Последствия

- Источник событий не знает о потребителях: добавить новый сервис-потребитель можно без изменений в источнике.
- Если потребитель недоступен, события копятся в его очереди и обрабатываются после восстановления.
- RabbitMQ гарантирует доставку «как минимум один раз», поэтому возможны повторы. Потребители обязаны быть идемпотентными (см. [ADR-004](ADR-004-idempotency.md)).
- Если недоступен сам брокер, события не теряются благодаря outbox (см. [ADR-003](ADR-003-outbox.md)).
- Историю событий из брокера восстановить нельзя. Если она понадобится (например, для аудита), будем хранить ее отдельно.
